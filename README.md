# مَدَد — MADAD

## Project overview

مَدَد سوق جملة يربط صاحب المتجر بالمورد. الواجهة عربية ومن اليمين إلى اليسار.

الخادم هو Supabase: المصادقة، PostgreSQL، وسياسات الصفوف. إذا غاب إعداد المشروع يعمل التطبيق في وضع التجربة المحلي من غير أن يتوقف.

اسم الحزمة الداخلي `rafd_v01`. الاسم الظاهر للمستخدم «مَدَد».

المستودع: https://github.com/lupstapp/Madad_v01

## The problem the application solves

شراء الجملة موزّع بين المكالمات ورسائل واتساب وقوائم أسعار غير محدّثة. مَدَد يجمع الموردين والمنتجات وسعر الجملة والحد الأدنى والسلة وتأكيد الطلب في مسار واحد.

## Target audience

صاحب متجر صغير أو متوسط يريد الشراء بالجملة، ومورد يريد إدارة منتجاته ورؤية الطلبات الواردة على منتجاته.

## Main features

- في الوضع المتصل: تسجيل وإنشاء حساب بالبريد وكلمة المرور، كتالوج من قاعدة البيانات، مفضلة، طلب بسعر يحسبه الخادم، وإضافة منتج للمورد.
- في وضع التجربة: دخول محلي لمتجر «بقالة النور» أو لمورد «واحة الغذاء للجملة» على بيانات `MockCatalog`.
- تصفح التصنيفات والموردين والمنتجات والبحث.
- تفاصيل المنتج، الكمية، السلة، والمفضلة.
- تأكيد الطلب بدفع عند الاستلام أو تحويل بنكي، ثم شاشة النجاح وطلباتي.
- للمورد: لوحة مختصرة، منتجاته، إضافة منتج، والطلبات التي تضم منتجاته.

## Screens and user flow

1. البداية: الشعار والعبارة «قيمة تتبادل، وأعمال تنمو». في وضع التجربة تظهر رسالة تطوير.
2. التعريف: ثلاث صفحات، ثم «ابدأ الآن» أو «تخطي».
3. الدخول المتصل: بريد وكلمة مرور، أو إنشاء حساب مع اختيار متجر أو مورد. الجوال جزء من ملف المنشأة وليس اسم الدخول.
4. الدخول التجريبي: «دخول تجريبي» و«دخول كمورد» يظهران فقط في وضع التجربة.
5. المتجر: الرئيسية، التصنيفات، طلباتي، المفضلة، حسابي.
6. المنتج ثم السلة ثم تأكيد الطلب ثم النجاح ثم طلباتي.
7. المورد: الرئيسية، منتجاتي، الطلبات، حسابي.
8. تسجيل الخروج ينهي جلسة Supabase في الوضع المتصل، ويمسح السلة والمفضلة المحلية.

## Technologies and packages used

- Flutter وDart مع null safety.
- `flutter_bloc` لإدارة الحالة عبر Cubit.
- `shared_preferences` للتخزين المحلي.
- `supabase_flutter` للعميل.
- `flutter_localizations` مع `Locale('ar', 'SA')` واتجاه RTL.
- خط Tajawal وصور منتجات محلية داخل `assets/`.

لا تُستخدم Firebase ولا Dio. لا يُرفع ملف إلى Supabase Storage؛ الصورة حقل لاحق.

## Architecture and folder structure

```text
lib/
  main.dart                 يهيّئ Supabase إن وُجد الإعداد، وإلا وضع التجربة
  app/                      التطبيق، النطاق، والمسارات
  core/                     الثيم والتخزين المحلي والإعداد
  data/
    mock/                   MockCatalog لوضع التجربة والاختبارات
    models/
    remote/madad_store.dart عميل Supabase
    repositories/           CatalogRepository و CommerceRepository
  features/                 الشاشات وCubits
supabase/migrations/        المخطط وسياسات الصفوف ودالة الطلب
```

المسار: الشاشة → Cubit → المستودع → Supabase أو الذاكرة المحلية.

مجلد `core/` في جذر المستودع بقايا مشروع رَفْد. لا يستورده `lib/`، والتحليل يستبعده في `analysis_options.yaml`. لم يُحذف لأنه خارج مسار التشغيل.

## State management approach

`SessionCubit` و`CartCubit` و`FavoritesCubit` و`OrdersCubit` و`ShellCubit`. الكتالوج في `CatalogRepository`. الشاشات تقرأها عبر `MadadScope`.

في الوضع المتصل لا يُعدّ العلم المحفوظ في `shared_preferences` دليل دخول. الاستعادة تقرأ جلسة Supabase.

## Supabase Authentication

- إنشاء حساب وتسجيل الدخول بالبريد وكلمة المرور.
- تسجيل الخروج عبر `auth.signOut`.
- استعادة الجلسة عند الإقلاع، مع الاستماع إلى تغيّر حالة المصادقة.
- رسائل التحقق والأخطاء بالعربية.
- رقم الجوال يُحفظ في `profiles` ولا يُعامل كبريد.

دور الحساب في قاعدة البيانات: `customer` أو `supplier`. واجهة المتجر تقابل `customer`. الدور يُكتب مرة واحدة عند إنشاء المستخدم من البيانات الوصفية للتسجيل، ثم يمنع مشغّل التحديث تغييره أو تغيير `supplier_id` من جلسة المستخدم.

قيد أمني: المستخدم يستطيع عند التسجيل فقط إرسال `role=supplier` داخل البيانات الوصفية. لا توجد موافقة إدارية ولا مطالبة مخصصة في الرمز (custom claim). سحب الدور بعد ذلك يحتاج دالة أو لوحة بصلاحية أعلى من المفتاح العام.

## Database usage

المخطط الأول: `supabase/migrations/20260926005500_madad_schema.sql`.

الإضافة: `supabase/migrations/20260926120000_roles_and_secure_orders.sql`.

| الجدول | الغرض |
| --- | --- |
| `categories` | التصنيفات |
| `suppliers` | الموردون |
| `supplier_categories` | ربط المورد بالتصنيف |
| `products` | المنتجات وسعر الجملة والمخزون |
| `profiles` | ملف المنشأة، و`role`، و`supplier_id` للمورد |
| `favorites` | المفضلة، المفتاح `(user_id, product_id)` |
| `orders` | الطلبات |
| `order_items` | البنود بسعر نُسخ من جدول المنتجات |

المستخدم الجديد يحصل على صف في `profiles` عبر `handle_new_user`. الصفوف القديمة تأخذ الدور `customer`. حساب المورد ينشئ صفًا في `suppliers` ويربطه بـ `profiles.supplier_id`.

## Secure order RPC

`create_secure_order` دالة `security definer` تقبل معرفات المنتجات والكميات والعنوان وطريقة الدفع والملاحظة. لا تقبل سعرًا من الجهاز.

داخل معاملة واحدة:

- ترفض الجلسة الغائبة والكمية غير الصالحة والمنتج غير الموجود والكمية الأقل من الحد أو الأكبر من المخزون.
- تقرأ `wholesale_price` من `products`.
- تحسب المجموع ورسوم التوصيل: 25، وتصير 0 إذا بلغ المجموع 500.
- تنشئ الطلب وبنوده وتخصم المخزون.
- تُرجع معرف الطلب مع البنود والأسعار.

أُلغي إدراج `orders` و`order_items` المباشر عن `authenticated` حتى لا يكتب الجهاز السعر.

## Required Row Level Security policies

السياسات مفعّلة. لم تُعطَّل.

- قراءة الكتالوج لـ `anon` و`authenticated`.
- قراءة وتعديل `profiles` لصاحب `auth.uid()` فقط، مع منع تغيير الدور وربط المورد.
- المفضلة لصاحبها، والإدراج عبر `upsert` على المفتاح المركب.
- المورد يدرج ويعدّل ويحذف منتجات `supplier_id` المطابق لملفه فقط. المتجر لا يملك هذه السياسات.
- قراءة الطلب لصاحب الطلب، وللمورد إذا كان أحد البنود لمنتج يملكه.
- إنشاء الطلب يتم عبر الدالة فقط.

المفتاح العام لا يغني عن السياسات. مفتاح الخدمة يتجاوزها ولا يُشحن مع التطبيق.

## Local storage and caching

يُحفظ على الجهاز:

- اكتمال التعريف.
- سلة التسوق إلى أن يُؤكد الطلب.
- آخر كتالوج نجح تحميله.
- آخر قائمة مفضلة ناجحة.
- آخر طلبات نُزّلت، للعرض السريع.

عند انقطاع الشبكة تبقى آخر نسخة ظاهرة. فشل التحديث لا يمسحها. المفضلة: بعد الدخول الناجح تستبدل النسخة المحلية بقائمة الخادم حتى لا تتكرر. الكتابة الفاشلة تُرجَع محليًا. لا توجد طابور مؤجّل للعمليات التي فشلت أثناء انقطاع الشبكة.

وضع التجربة لا يتصل بالخادم، وجلسته المحلية خاصة به.

## Demo Mode versus connected mode

| | وضع التجربة | الوضع المتصل |
| --- | --- | --- |
| متى | غياب `SUPABASE_URL` أو `SUPABASE_ANON_KEY`، أو فشل التهيئة | وجود القيم ونجاح `Supabase.initialize` |
| الدخول | أزرار محلية مع رسالة تطوير | بريد وكلمة مرور |
| الكتالوج | `MockCatalog` | جداول Supabase |
| الطلب | يُحسب على الجهاز | `create_secure_order` |
| المفضلة والمنتجات المضافة | على الجهاز | على الخادم مع نسخة محلية |

لم يُتحقق من مشروع Supabase حي في هذا المستودع. الاختبارات تستخدم محاكاة ولا تفتح الشبكة.

## Required environment variables

- `SUPABASE_URL`
- `SUPABASE_ANON_KEY`

لا تُكتب القيم في المصدر. لا يُستخدم مفتاح الخدمة.

```bash
flutter run \
  --dart-define=SUPABASE_URL=[YOUR_SUPABASE_URL] \
  --dart-define=SUPABASE_ANON_KEY=[YOUR_SUPABASE_ANON_KEY]
```

من غير هذين المتغيرين:

```bash
flutter run
```

## Setup instructions

```bash
flutter pub get
supabase link --project-ref YOUR_PROJECT_REF
supabase db push
```

في لوحة Authentication عطّل تأكيد البريد إن أردت دخولًا مباشرًا بعد التسجيل، أو اتركه: التطبيق يعرض رسالة لتأكيد البريد ثم تسجيل الدخول. التسجيل كمتجر يكتب `customer`. التسجيل كمورد يكتب `supplier` وينشئ منشأة المورد. تغيير الدور لاحقًا من التطبيق مرفوض.

## How to run the project

```bash

flutter run \
  --dart-define=SUPABASE_URL=[YOUR_SUPABASE_URL] \
```
